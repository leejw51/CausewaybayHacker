# Shared fixtures

Plain JSON, read by the Rust suite and the TypeScript suite alike. Nothing in
this directory is hand-typed: every value came out of a tool, and the command
that produced it is recorded beside it.

The point of a fixture here is that **two implementations that never see each
other's code still agree**. A value that QA computed itself would only prove
that QA agrees with QA, so none of these are computed here.

```
tests/vectors/
├── generate.py              regenerates addresses.json and signatures.json
├── addresses.json           SPEC §9.1 — mnemonic → EVM address
├── signatures.json          SPEC §9.2 — the §3.2 challenge, signed
└── mistakes/
    ├── generate.py          recompiles every case and rewrites expected.json
    ├── expected.json        SPEC §9.7 — file → kind, code, phase
    ├── rust/*.rs            one source per taxonomy row
    ├── rust/*.rustc.json    the real `rustc --error-format=json` output
    ├── go/*.go
    ├── go/*.gobuild.txt     the real `go build` output
    ├── */*.runtime.txt      the real panic / fatal output, where there is one
    └── content/*.rustc.json the same, for starters that ship in content/**
```

Read alongside `tests/PLAN.md`, which says what each of these is for and what
state the test that consumes it is actually in.

Regenerate everything:

```bash
python3 tests/vectors/generate.py
python3 tests/vectors/mistakes/generate.py
```

Both take `--check`, which exits non-zero if the committed file would change.
That is the CI form: a generator whose output drifted silently is a generator
that has moved the goalposts.

## `addresses.json` — SPEC §9.1, address conformance

If the frontend's derivation drifts from `CausewaybayWallet`'s, a user's
account becomes a different account and their cleared map is gone. This file
is the thing that catches it before a user does.

**Generated by** `CausewaybayWallet`'s own binary, **`cwbwallet 1.0.4`**,
found at `../CausewaybayWallet/rustcli/target/debug/cwbwallet` relative to
this checkout. Override with `$CWBWALLET`. Build it with `make -C
../CausewaybayWallet build`, or `cargo build` in its `rustcli/`.

One command per row:

```bash
cwbwallet --json --home <throwaway> utils derive --mnemonic "<phrase>" --index <i>
```

`utils derive` is the wallet's offline calculator — its own help says
"Nothing is stored and nothing is remembered" — which is why it cannot touch
a real wallet store. A throwaway `--home` is passed anyway, because a claim in
a help string is not a guarantee. `--home` rather than `CAUSEWAYBAY_HOME`:
the wallet deliberately does not let clap read that variable, so the flag is
the form whose precedence is settled.

**Cross-checked.** Every row that also appears in
`CausewaybayWallet/testvectors/derivation.json` — 10 of them — is asserted
equal to it. That file was generated from `eth-account`, an independent
implementation, so a value in `addresses.json` is one that *three* things
agree on: the wallet's Rust core, `eth-account`, and (once §9.1 is wired up)
the frontend's `@scure` + `@noble` stack. The generator refuses to write the
file if the wallet CLI and the vectors disagree, and says which row drifted.

### Shape

```jsonc
{
  "generated_by": { "tool": …, "version": "cwbwallet 1.0.4", "command": … },
  "cross_checked_against": { "checked": true, "rows_compared": 10, … },
  "path_template": "m/44'/60'/0'/0/{index}",
  "mnemonics": [
    {
      "name": "bip39-canonical",
      "phrase": "abandon abandon … about",
      "accounts": [
        {
          "index": 0,
          "path": "m/44'/60'/0'/0/0",
          "address": "0x9858EfFD232B4033E47d90003D41EC34EcaEda94",  // EIP-55
          "address_lower": "0x9858effd…",   // SPEC §3.4: what the DB stores
          "private_key": "0x…",
          "public_key_compressed": "0x…"
        }
      ]
    }
  ]
}
```

`address` is the checksummed form (`users.address_eip55`); `address_lower` is
the primary key and the directory name (SPEC §3.4). Both are in the file
because the §3.4 test is "these two spellings must never become two players",
and a test needs both spellings to assert it.

### The mnemonics, and why these

All three are published in someone else's documentation. None of them could be
mistaken for a real user's phrase.

| name | why it is safe to print | anchor |
| --- | --- | --- |
| `bip39-canonical` | `abandon ×11 about` — the all-zero-entropy BIP-39 English test vector | the BIP-39 spec |
| `foundry-anvil-default` | `test ×11 junk` — what Anvil and Hardhat print on startup | index 0 is `0xf39Fd6e5…92266`, on every local node anyone has run |
| `bip39-legal-winner` | the second BIP-39 English test vector | the BIP-39 spec |

## `signatures.json` — SPEC §9.2, signature round trip

The frontend signs; the backend recovers. They must agree on the **exact
bytes**, and EIP-191 hashes the message's byte *length*, so a single stray
newline makes the digest completely different and the login fails with no
clue why.

**Generated by** the same `cwbwallet 1.0.4`, along three separate paths that
must all agree:

```bash
# the signature
cwbwallet --json utils sign --private-key <k> --message "<msg>"
# the digest, assembled independently and hashed
cwbwallet --json utils keccak --hex <0x19 || "Ethereum Signed Message:\n" || len || msg>
# the recovery
cwbwallet --json verify --message "<msg>" --signature <sig> --address <addr>
```

The digest path was itself checked against the wallet's published
`testvectors/eip191.json` (generated from `eth-account`): all four of its
vectors — including the empty string and a non-ASCII one — reproduce both the
`prefixed_hash` and the `signature` byte for byte.

### Two things this fixture had to decide, now settled by PROTOCOL.md

Both were ambiguous in SPEC §3.2 when the fixture was generated, and both
were resolved the same way by `PROTOCOL.md` §4.2, which is now the authority
for the wire. The fixture was written first and did not have to change.

1. **No trailing newline.** SPEC §3.2 prints the message in a fenced block,
   which does not settle whether it ends with `\n`. PROTOCOL.md §4.2 settles
   it: "four lines, `\n`-separated, no trailing newline". The fixture records
   it three ways — `message` (a JSON string with explicit `\n`),
   `message_hex` (the UTF-8 bytes) and `message_len` (the number that goes
   into the EIP-191 prefix) — so no implementation can differ from another
   without this file catching it. EIP-191 hashes the byte *length*, so a
   single stray newline makes the digest completely different and the login
   fails with no clue why.

2. **`(EIP-55)` is an annotation, not text.** SPEC §3.2's second line reads
   `address: 0xAbC…                (EIP-55)`. The parenthetical says how the
   address is spelled; it is not part of the signed message. PROTOCOL.md §4.2
   gives the message without it.

PROTOCOL.md §4.2 also adds the rule this fixture cannot express on its own:
**sign `message` byte-for-byte as given, never rebuild it from the parts.**
`tests/smoke/contract.mjs` §8.6 is the test for that — it signs the server's
own string, and separately signs a reconstruction with one trailing newline
and requires the server to refuse it.

### `v`, which is the likeliest interop bug in the whole auth path

The last byte of `r||s||v` in these vectors is `0x1b` or `0x1c` — **27 or 28**,
the Ethereum convention. `k256`'s `RecoveryId`, which SPEC §3.2 step 4 says
the server recovers with, is **0 or 1**. A verifier that hands 27 straight to
`k256` fails every login. PROTOCOL.md §4.3 requires **both** to be accepted
("`v` is 27 or 28; 0 or 1 is also accepted and normalised"), so both
spellings are in each vector:

```jsonc
{ "signature": "0x…1c", "v": 28, "recovery_id": 1, "r": "0x…", "s": "0x…" }
```

### `must_reject`

Four signatures that must **not** authenticate, each with the error code the
server owes: a flipped parity, an all-zero 65 bytes, a 64-byte truncation, and
a perfectly valid signature by the wrong key. A verifier that only ever sees
good input passes by accident.

## `mistakes/` — SPEC §9.7, mistake classification

One source file per row of the SPEC §7.1 taxonomy, in each of the four
lands, **actually compiled** on this machine, with the compiler's real output
captured beside it. BE's classifier can be unit-tested against
`rust/*.rustc.json`, `go/*.gobuild.txt`, `cpp/*.cxx.txt` and
`python/*.pycompile.txt` (and the `*.runtime.txt` next to them) with no
toolchain installed at all, which is the point: a classifier tested against
hand-written "what rustc probably says" is a classifier tested against a
guess.

**Toolchain:** `rustc 1.97.1 (8bab26f4f 2026-07-14)`, `go1.27.1 darwin/arm64`,
Apple clang 21 as `c++`, Python 3.13, Darwin 25.6.0 arm64. Recorded in
`expected.json` under `toolchain`, because a diagnostic is a property of a
compiler version, not of a language.

**Commands**, exactly SPEC §5.1's:

```bash
rustc --edition 2021 -O --error-format=json main.rs -o prog    # then ./prog
go build -o prog main.go                                        # then ./prog
go vet ./main.go            # the unhandled-error row only
go run -race main.go        # the data-race row only
c++ -std=c++20 -O2 -pthread -o prog main.cpp                    # then ./prog
python3 -m py_compile main.py                                   # then python3 -I main.py
```

Each source is copied into a fresh temp directory as `main.rs` / `main.go` /
`main.cpp` / `main.py` and compiled there, so the `file_name` in every
captured span is the relative `main.rs` — not an absolute path from this
machine baked into a fixture that runs on another.

**C++ captures are per toolchain.** `c++` is clang on macOS and gcc on Linux,
and they word one mistake two ways (`use of undeclared identifier` versus
`was not declared in this scope`), so a C++ case is captured once per
toolchain id — `cpp/segfault.clang-darwin.cxx.txt`, and `gcc-linux` beside it
once a Linux machine has run the generator — with the id in the case as
`cxx` and the list under `cpp_toolchains_captured`. A machine regenerates and
checks only the toolchain it has and carries the others over untouched; a
toolchain the repo has no captures for is a note from `--check`, not a
failure, because the machine reporting the gap is the one that cannot fill
it. A segfault prints nothing, so the runtime capture for it is the
placeholder `<signal 11>` and the case records `run_signal`.

### `expected.json` shape

```jsonc
{
  "toolchain": { "rustc": …, "go": …, "host": … },
  "cases": [
    {
      "file": "rust/borrow-after-move.rs",
      "lang": "rust",
      "kind": "borrow-after-move",     // the §7.1 slug the classifier must produce
      "code": "E0382",                 // the identity it keys off; null if none
      "phase": "compile",              // compile | lint | runtime | tool
      "level": "error",                // error | warning | panic | fatal
      "compile_time": true,            // true for compile and lint
      "compiles": false,
      "verified": true,                // the generator re-ran it and saw this
      "assert_me": true,               // false = a documented gap, do not assert
      "captured": "rust/borrow-after-move.rustc.json",
      "observed": { "identities": ["E0382"], "diagnostics": [ … ] }
    }
  ],
  "kinds_covered": [ … ],
  "kinds_not_covered": { "wrong-answer": "…", "timeout": "…" },
  "known_gaps": { "go/unhandled-error.go": "…" },
  "code_collisions": { "rust:E0277": { "kinds": ["missing-trait", "unhandled-error"] } },
  "unverified_cases": []
}
```

**`phase` is four values, not two**, because the taxonomy has rows that do not
behave alike:

* `compile` — the build fails. Most rows.
* `lint` — the build **succeeds** and the diagnostic is a *warning*. Rust's
  `unused` row is this: `rust/unused.rs` compiles and runs fine. A classifier
  that only reads the error stream will never see it.
* `runtime` — the build succeeds and the program dies. `index-range`,
  `nil-deref`, `deadlock`.
* `tool` — needs something that is not the plain build: `go vet`, `go -race`.

### Two groups of cases

* **42 synthetic sources** under `rust/`, `go/`, `cpp/` and `python/`, one or
  more per taxonomy row, written to isolate one diagnostic each.
* **6 real starters** from the shipped content, under `content_starter_cases`
  in `expected.json`. These are worth more than the synthetic ones beside
  them: they are the exact bytes a player's editor opens with, so the
  classifier's first real input on day one is one of these.

  The **source is not copied here.** It lives in `content/**`, PM owns it,
  and a copy would drift. The generator reads the `starter` out of the TOML
  at generate time and captures the compiler output into
  `mistakes/content/<quest_id>.rustc.json`, which is all a classifier needs
  offline. If a quest is renamed or its starter fixed, the generator says so
  instead of silently testing a stale copy.

  | quest | kind | code |
  | --- | --- | --- |
  | `rust.advanced.02.the-move` | `borrow-after-move` | E0382 |
  | `rust.advanced.02.move` | `lifetime` | **E0373** |
  | `rust.advanced.05.rwlock` | `mutability` | E0596 |
  | `rust.advanced.06.lifetimes` | `lifetime` | E0106 |
  | `rust.advanced.07.generics` | `type-mismatch` | E0308 |
  | `go.advanced.12.chan-directions` | `other` | `go:invalid-operation` |

  Two rows have moved since they were first written, which is the arrangement
  working rather than failing: `the-move` came over from `rust/basic` when
  BASIC became grammar drills, and `chan-directions` replaced
  `go.advanced.09.errors-in-flight` once PM fixed that starter into
  compiling. Both were noticed because the generator reads the pack, not a
  copy.

### Coverage, honestly

48 of 48 cases verified against the real toolchains. Sixteen of the
taxonomy's seventeen kinds have at least one verified fixture — `wrong-answer`
joined the list with Python's `RecursionError`, the one place §7.1 gives that
verdict a compiler identity.

**Not covered, and why:**

| row | status |
| --- | --- |
| `unhandled-error` (go) | **no fixture.** §7.1 maps it to "`err` assigned and not checked (vet)". Plain `go vet` — the standard analyzer set — says nothing about a discarded error; that check is `errcheck`, a separate tool not in the Go distribution. The source and the captured `go vet` output (exit 0, empty) are kept as the evidence. Either BE vendors `errcheck` or the row loses its Go half. |
| `wrong-answer` | **N/A here.** A verdict, not a compiler identity — the program compiles, runs, prints the wrong thing. It belongs to SPEC §9.6 / the runner suite. |
| `timeout` | **N/A here.** Also a verdict. Its fixture is an infinite loop and what is asserted is the SIGKILL, not a diagnostic. `tests/PLAN.md` owns it. |

**Three findings BE should read before writing the classifier:**

* **`E0373` is in no row of SPEC §7.1's table** — and it is what a *shipped
  quest's own starter* produces (`rust.advanced.02.move`, "closure may
  outlive the current function"). §7.1 says an unmatched code is stored as
  `other` with the code kept, which is legal; filing a quest's own starter
  under `other` on the player's first encounter with the training loop is a
  poor first impression. Recorded in `expected.json` under
  `rust_codes_outside_the_71_table` and proposed to PM in
  `docs/decisions.md`.

* **`rust:E0277` maps to two kinds.** `missing-trait` (`{:?}` on a struct with
  no `Debug`) and `unhandled-error` (`?` in a `fn main()` returning `()`) are
  the *same code*. §7.1 lists both. The code alone cannot decide; the
  classifier needs the message text or the span. Both fixtures are present so
  the disambiguation has something to be tested against.
* **`data-race` is a sampling detector, not a proof.** `go run -race` caught
  the race in 3 of 3 runs here, and `race_detected_runs` records that — but
  the detector reports what it observed, and a build on a quieter machine may
  observe nothing. Treat this one row as advisory in CI, not as a gate.

### The Go environment

Every Go case is built with SPEC §5.1's environment: `GOCACHE`, `GOMODCACHE`,
`GOPATH` under a scratch root, `GOFLAGS=-mod=mod`, and **`GOPROXY=off`**. All
of them build with no network and no `go.mod` — they are single-file `package
main` programs importing only the standard library, which is deliberate: a
fixture that needed a module download would not be a fixture.
